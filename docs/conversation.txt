# Visit subsystem feature plan

## User

Help me create a plan to implement a new feature: Build a runnable Spring Boot web app "visit-subsystem"
for pharmaceutical MR (medical representative) to visit management.

Goal
Manage the academic-visit lifecycle: plan -> check-in -> check-out (with compliance)
-> call report -> monthly dashboard.

Minimal Functional requirements
1) Data model: Hospital(name, lat, lng); Hcp/Doctor(name, hospital); Product(name);
   Visit(hcp, product, departmentName, plannedAt, checkInAt/lat/lng,
   checkOutAt/lat/lng, duration, status, complianceFlag, abnormalReasons);
   CallReport(visit, talkingPoints, feedback, materialsDistributed).
2) Five steps:
   - Plan visit: choose HCP, product, department, planned time. Status = PLANNED.
   - Check in: record SERVER time + GPS(lat,lng)(manually input, simulate mobile device capture). PLANNED -> CHECKED_IN.
   - Check out: record time + GPS, compute duration seconds, run compliance. -> CHECKED_OUT.
   - Compliance: ABNORMAL if duration < 5 minutes OR distance from hospital > 500 m.
     Use great-circle distance, NOT Euclidean distance on raw degrees.
     Persist flag (OK/ABNORMAL) + reason codes.
   - Call report: only after check-out; save talking points, feedback, materials
     distributed. Status -> REPORTED.
3) Pages: Thymeleaf forms to plan / check-in / check-out / report, a visit list, and a
   monthly dashboard of visit counts per product (with a chart).
4) REST endpoints mirroring the steps.

Technical constraints
- Java 21, Spring Boot 3, Maven.
- H2 embedded file DB (runs with no external DB) + Flyway migrations for schema and seed data.
- JUnit tests for the compliance algorithm (incl. boundary cases) and the Haversine math.
- A multi-stage Dockerfile and a docker-compose.yaml for deployment.

How to work
- Go in small phases and STOP after each so I can review:
  (1) scaffold, (2) schema+entities, (3) compliance+service+tests,
  (4) web+REST+pages, (5) dashboard, (6) docker.
- Do NOT invent version numbers, dependency coordinates, or API signatures.
  If unsure, say so and verify against official docs.
- After each phase, give me the exact command to verify it runs.
- Call out every assumption/tradeoff explicitly.
Begin with Phase 1 ONLY.

# Phase 2 — Schema + entities (only this phase)

## Starting point (verified)
Phase 1 scaffold is in place: Boot 3.5.16, Java 21, `application.yml` (H2 file DB `./data/visitdb`, `ddl-auto: validate`, Flyway on with 0 migrations, H2 console at `/h2-console`). Flyway 11.7.2 + H2 2.3.232 come from the Boot BOM.

## Decisions (from your answers)
- **Plain Java getters/setters, no Lombok** — no annotation processors.
- **abnormalReasons = one `VARCHAR` column** on `visit`, comma-joined codes via a JPA `AttributeConverter` (`Set<AbnormalReason>` ⟷ `VARCHAR(200)`).
- Long `BIGINT IDENTITY` PKs, enums stored as `VARCHAR` (`@Enumerated(STRING)`), timestamps as `Instant` (UTC).

## Mapping gotchas handled up front (so `validate` stays green)
- Hibernate 6.6 maps `Instant` → `TIMESTAMP_UTC`, so migration columns must be `TIMESTAMP(6) WITH TIME ZONE`.
- Hibernate maps `Double` → `DOUBLE PRECISION`.
- Boot's naming strategy maps camelCase → snake_case (`checkInLat` → `check_in_lat`); no explicit `@Column` names needed except the reasons column.
- `ddl-auto: validate` is already enabled, so tests and startup both fail fast if DDL and mappings drift — that's the verification mechanism.

## Files to create

### Migrations (`src/main/resources/db/migration/`)
**`V1__schema.sql`** — dependency-ordered DDL:
- `hospital(id PK, name VARCHAR(200) NOT NULL, lat DOUBLE PRECISION NOT NULL, lng DOUBLE PRECISION NOT NULL)`
- `product(id PK, name VARCHAR(200) NOT NULL)`
- `hcp(id PK, name VARCHAR(200) NOT NULL, hospital_id REFERENCES hospital)`
- `visit(id PK, hcp_id REFERENCES hcp, product_id REFERENCES product, department_name VARCHAR(200) NOT NULL, planned_at TIMESTAMP WITH TIME ZONE NOT NULL, check_in_at/check_in_lat/check_in_lng, check_out_at/check_out_lat/check_out_lng, duration_seconds BIGINT, status VARCHAR(20) NOT NULL, compliance_flag VARCHAR(20), abnormal_reasons VARCHAR(200))`
- `call_report(id PK, visit_id BIGINT NOT NULL UNIQUE REFERENCES visit, talking_points VARCHAR(4000), feedback VARCHAR(4000), materials_distributed VARCHAR(1000))`
- Indexes on `visit(hcp_id)`, `visit(planned_at)` (for the Phase 5 monthly dashboard), `hcp(hospital_id)`.

**`V2__seed_data.sql`** — fictional seed: 2 hospitals with plausible lat/lng (Beijing ~39.9087,116.3975; Shanghai ~31.2304,121.4737), 3 products (Cardiolex, Neurocare, Oncofine), 3 HCPs across the two hospitals; fixed IDs 1..n, then `ALTER TABLE ... ALTER COLUMN id RESTART WITH 100` per table so future inserts don't collide.

### Enums (`domain/`)
`VisitStatus` (PLANNED, CHECKED_IN, CHECKED_OUT, REPORTED), `ComplianceFlag` (OK, ABNORMAL), `AbnormalReason` (SHORT_DURATION, FAR_FROM_HOSPITAL).

### Entities (`domain/`) — plain classes, no-arg ctor + getters/setters, LAZY associations
`Hospital`, `Product`, `Hcp` (→ Hospital), `Visit` (→ Hcp, → Product, `Set<AbnormalReason>` via converter), `CallReport` (one-to-one → Visit, unique join column; mapped one-way to avoid lazy cycles).

### Converter (`domain/`)
`AbnormalReasonSetConverter` — stable-order comma join, empty set ⟷ `null`, tolerant parsing.

No repositories yet (they land with the service in Phase 3). No config changes needed.

## Assumptions / tradeoffs (new in this phase)

- **Time handling**: form input from `<input type="datetime-local">` is interpreted in the **server's default zone** and stored as UTC `Instant`; templates render back in the server zone via `DisplayFormats`. A per-user timezone is not modeled.

- **API error shape** uses RFC 7807 `ProblemDetail` (Boot's default for `spring.mvc.problemdetails`-style errors) — no custom envelope.
- **`ReportRequest` has no validation** (`talkingPoints`/`feedback` optional per spec); `PlanVisitRequest` and `GpsRequest` are validated.
- **409 on `DataIntegrityViolationException`** is broad — it will also catch other integrity errors. Acceptable now; can narrow by inspecting the constraint name later.
- **No JS** for GPS capture or the chart (chart is Phase 5); GPS fields are plain number inputs, as the requirement says the capture is simulated.

## Root cause

`YearMonth` exposes **two** "month" accessors:

- `getMonthValue()` → `int` `1–12`  → Thymeleaf property `monthValue`
- `getMonth()` → `Month` **enum** (`DECEMBER`) → Thymeleaf property `month`

The previous/next links used `${prev.month}` / `${next.month}`, so the template emitted `?month=DECEMBER`, and the controller's `@RequestParam Integer month` failed to convert it — the `MethodArgumentTypeMismatchException` you saw. It only "worked" visually because the page still rendered from the default month; the actual link click 400'd.

## Fix

```25:26:src/main/resources/templates/dashboard.html

            <a class="button secondary" th:href="@{/(year=${next.year},month=${next.monthValue},status=${data.statusFilter})}">Next month</a>
```

Now emits `?year=2025&month=12` and `?year=2026&month=2`.
